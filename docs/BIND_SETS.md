# Bind sets

A game's page has a **Binds** section: several named sets of controls for that game, **one in use at a time**. A set can carry controller binds (what each controller button and stick does when the controller is a keyboard and mouse), an on-screen touch layout, or both.

* **A layer, not a setting.** Using a set never writes the game's own Controls or Engine settings. With none in use ("Standard") nothing changes. A deleted set that was in use falls back to Standard.
* **Controller part** (`PadPart`): only what differs from the standard layout, plus the right stick's up-and-down speed. Using a set with this part puts the controller into keyboard-and-mouse mode for that game (`PadInput.beginSession`).
* **Touch part** (`TouchLayout`): controls placed by fractions of the screen (so any screen shape works): keys (a plain press: down while touched, never shorter than a tap, so tapping taps and holding holds; or "latch", each tap switches the key on or off), the three mouse buttons, the wheel, W A S D or arrow sticks, a **Look / Mouse** button (action `lookmode`, touch-only: it flips the screen between looking and a normal mouse for this session without changing the layout's own look setting; the Hub's `binds.js` accepts it on touch layouts only, as `TOUCH_ONLY_ACTIONS`; the live Hub was restarted with this on 2026-10-07), plus "drag to look". Old `mode` values "tap" and "hold" are the same press. Drawn by `CustomControlsView` in place of the built-in layouts while the set is in use. The editor sits over the game itself (see below).
* **Files:** a set exports to `.portholebinds` (plain JSON, `BindSetFile`) and imports from one. Everything read from a file is checked: unknown actions and out-of-range numbers dropped, text cleaned and cut, 40 controls at most, 64 KB at most.
* Code: `Core/BindSets.swift` (data and files), `UI/CustomControls.swift` (drawing), `UI/Game/GameBindsSection.swift` (the section, the set editor and the touch layout editor). Tests: `app/Tests/Engine/run.sh`.

## In the game

The running game's menu has **Binds** (a sheet over the game: pick the set in use, make a new one from your current controls, edit a set) and the **pencil** button that is always on screen while a game runs (the menu has the same **Edit on-screen controls**). Everything applies at once: `SessionController.bindSetsChanged` re-reads the game's sets whenever they change (`SessionView` watches `AppModel.games`), updates the on-screen layout and, when what the controller does has changed, `PadInput.updateLive` (held keys are only released when that really changed). The on-screen editor is `ControlsEditorView` (`UI/ControlsEditor.swift`: top bar with Done / + Add / Undo / Redo / Presets / Look, a tray of things to add, and a settings panel for the selected control) driving `CustomControlsView`: while editing, a touch never reaches the game; it selects, moves (snapping to the centre and to other controls), resizes (corner dot, pinch or slider) or, from the tray, drops a new control. Pressing Done plays with the controls as they are. The tray under **+ Add** scrolls with a quick swipe; hold a tile for a moment to pick it up and drag it where you want it. The game's top bar also has a **keyboard** button next to Menu and the pencil (`GameHUDView.keyboardButton`). `UI/ControlsKit.swift` holds the key button and key tables so the editor can be tried alone: `app/Tests/ControlsEditor/build.sh --edit` builds a small simulator app around the real views. Each change is saved into the set in use (`saveLiveTouchLayout`); with no custom layout the pencil first makes a set from the layout in use (Mouse and keys, or First person) and uses it (`createLiveLayout`), so the built-in layouts are ordinary editable layouts. The controller type (Xbox or HID) and the controller-versus-keyboard choice of a game without a set are fixed at the start.

## Sharing (phase 2)

Sets can be shared on the Hub (`hub/binds.js`, in the Launcher project) so other people can find them for the same game.

* **Who:** no accounts. Each install signs its writes with the P-256 key it already uses for compatibility reports (`CompatIdentity`); the Hub registers the key on first use and caps writes per day, sets per game (5) and per install (30). Nothing that identifies a person or device is sent or stored.
* **A game's id** is the one compatibility reports use: `steam:<app id>` for a game downloaded through Steam, else `file:<32 hex of the program's fingerprint>` (`BindsShareStore.gameRef`).
* **What is public at once:** the controller binds, the touch layout (every control labelled by what it presses: E, Space, LMB ...), and the thumbs. **What is held until approved** (by you, in the Launcher's Reviews ▸ Key binds list or `node hub/binds-admin.js`): a set's name, its notes, the labels typed on its controls, and review comments. Until then a set is called "Shared set #id". Rejected text is removed and the set stays.
* **Checks both ways:** the Hub refuses anything outside the app's vocabulary (actions, positions, sizes, 40 controls, size limits); the app checks every download again (`BindsShare.localSet`) and never puts one in use by itself. Three different installs reporting a set hide it.
* **App:** a game's Binds ▸ Community ▸ *Shared binds for this game* (browse, read, add, rate, report) and, in a set's editor, *Share this set* / *Update* / *Stop sharing* (`UI/Game/SharedBindsViews.swift`, `Core/BindsShare*.swift`).
* **Tests:** `app/Tests/Engine/run.sh` and, in the Launcher project, `hub/test/binds.test.js` and `hub/test/contract.test.js`. The contract test feeds the Hub the exact payloads the app publishes (`fixtures/client-payloads.json`, written by the app's tests with `WRITE_FIXTURES=1`) and saves the Hub's answers (`fixtures/server-responses.json`) for the app's tests to decode. Copy the fixtures between the two projects when either side changes.
* **Going live** needs a `launcher-hub` pm2 restart. Until then the app says sharing is not switched on.
