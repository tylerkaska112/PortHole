# 0056 - what happens to a guest breakpoint (diagnostic)

0.50.100 (engine r16): Black Ops 3's protection now maps clean copies of System32 DLLs and goes through ~12 modules (`[sc] #1..#18`, 112 modules loaded), then dies with `NtTerminateProcess(0x80000003)`. Its threads execute `int3` at one guest address (0x70511364a0, handled three times: `[int3-guest]`, `call_seh_handlers [exc] code=80000003`) and finally on another (0x70770361a0) the exception reaches the root (`[unwind-root] ACCEPTING terminal root frame`) after one guest SEH handler (`blackops3.exe+0x2bc5494`) was called. `exception.c`: `[veh] 0056 AddVectoredExceptionHandler first= func=` (first 40), `[veh] 0056 breakpoint at ...: the vectored handler list is EMPTY`, and the existing `[veh] calling/returned` lines now also for EXCEPTION_BREAKPOINT. `signal_arm64ec.c`: `[seh] 0056 breakpoint at ...: handler ... returned N` (first 60). Logging only.

**Result (0.50.101 log) and 0057 (0.50.102).** The vectored handler list is empty at the int3s (the protection adds a VEH, uses it for a deliberate null-read exception - `returned ffffffff` - and removes it), and the game's own frame SEH handlers (`blackops3.exe+0x2bc3344`, `+0x2bc8054`) answer `1` = ExceptionContinueSearch for the breakpoint at 0x70511364a0 and at 0x70789361a0 (the latter ends in `NtTerminateProcess(0x80000003)`). On Windows they must claim it. 0057 dumps each such guest handler once: `[handler-dump] 0057 handler= image= control_pc= frame= func_entry= handler_data=`, the 96 bytes of handler data (the scope table), and its jump-linked code blocks (96 B each, up to 120, `block <addr>: <hex>`), so the decision can be read offline.

**0.50.102 result and 0058 (0.50.103).** The dumped handlers: `blackops3.exe+0x2bc3344` is MSVC's `__GSHandlerCheck` (calls a cookie check, always returns 1), `+0x2bc5494` is the exe's own `__C_specific_handler` (scope table walk). For the final int3 (in generated code at a fresh address, thread start stub 0x...c1b490) the chain is GS, GS, then `__C_specific_handler` for frame control pc +0x2bd349a whose scope table `{begin 0x2bd342b, end 0x2bd34b2, filter 0x2c68ca4, target 0x2bd34b2}` COVERS it, and it answers 1: the FILTER (obfuscated code at +0x2c68ca4) returned "continue search". 0058 dumps the filter's code blocks (`[handler-dump] 0057 filter#N block ...`, `scope data` lines) and logs `[uef] 0058 ...` (SetUnhandledExceptionFilter / the filter's answer / none set) and `[veh] 0058 RemoveVectoredExceptionHandler`.
