# 0064 - the kernel32 exports Windows 10 has and ours lacks, as stubs (Black Ops 3)

**Problem.** 0.50.108 log: with the module lists in Windows' order (0045) and every earlier barrier passed, Black Ops 3's protection spins at 100% CPU in ONE function with identical registers: `R9` = kernel32's base, `RBX` = kernel32's AddressOfNames, `R14` = its AddressOfNameOrdinals, `RDI` = 0x54e = 1358 = kernel32's NumberOfNames. It is its hash-based GetProcAddress (FNV-64: `mov r12, 0x100000001b3`, seed constants in the code) walking kernel32's export names for a hash that matches none of them, and retrying forever. The function exists in Windows' kernel32 (it only ever searches kernel32) but not in ours: the Windows 10 1909 kernel32 exports 1629 names ([kkent030315/kernel32-exports](https://github.com/kkent030315/kernel32-exports)), ours 1358; 326 are missing (many are internal/AppX/Wer/Termsrv/calendar functions).

**Change.** `wine/dlls/kernel32/ios_missing_exports.c` + `kernel32.spec` (`@ stdcall NAME() ios_k32_stub_NAME`) + `Makefile.in`: every missing name is exported as a stub that sets ERROR_CALL_NOT_IMPLEMENTED, returns 0 and logs its first 60 calls (`[k32-stub] 0064 NAME called`) - which names the function the game is after. kernel32.dll grows from 917504 to 1114112 bytes (SizeOfImage 0xc0000 -> 0xe0000). Rebuilt with `DEST=/tmp/k32 bash vendor/Madeira/build/wine-pe/build-modules.sh kernel32`, installed at `vendor/Madeira/app/Madeira/arm64ec-windows/kernel32.dll` (backup `$F4_BUILD_ROOT/backup-kernel32-before-0064.dll`). The name list is in /tmp/k32_missing.txt when rebuilt (regenerate from the kkent030315 README minus our export table).

**Risk.** The kernel32 image is bigger; a program that finds one of these names by GetProcAddress now gets a function that fails instead of NULL.

**0.50.109 result and 0065 (0.50.110).** With the 326 stubs the walk is unchanged (`RDI` = 0x694 = the new NumberOfNames, still no match, no `[k32-stub]` call): the function is not one of the names missing from our table. The remaining difference in the export table is the FORWARDER strings: 20 kernel32 exports forward to `kernelbase.<name>` in lowercase (`InitOnceBeginInitialize/Complete/ExecuteOnce`, `SetThreadToken`, `DiscardVirtualMemory`, `GetPackage*`, `GetCurrentPackage*`, `CreateFileMappingFromApp`, `MapViewOfFileFromApp`, `CtrlRoutine`, `AppPolicyGet*`) where Windows writes `KERNELBASE.<name>` (the 83 NTDLL ones are already uppercase). A resolver that follows forwarders by comparing/hashing the module part case-sensitively fails on those. The spec's 20 `kernelbase.` forwarders are now `KERNELBASE.` (Wine's own forwarder resolution is case-insensitive).
