# 0075 Dock host: start a program of the game next to Valve's client

`vendor/Madeira/madeira-dock/src/launch.c` (`run_own_program`), rebuilt into `arm64ec-windows/dockhost.exe`
(`x86_64-w64-mingw32-clang ... src/*.c`, as `tools/build.sh`; 44 KB).

Rust (Steam app 252490): Valve's client only starts the program its launch list names, `Rust.exe`, which starts Easy Anti-Cheat; that does not run here. `RustClient.exe` is the game and plays on servers that do not require it. Started without Steam (0.50.124/125) the game loaded its Steam libraries, then stalled at 99 % loading.

With `MADEIRA_DOCK_PROGRAM` (a Windows path; `MADEIRA_DOCK_PROGRAM_ARGS` optional) the host does everything it did before (authenticated session, entitlement to the app, verified install folder, custom-binary preparation, Steam discovery values published), then starts that program with `CreateProcessW` instead of calling `IClientAppManager::LaunchApp`. The program must be an `.exe` inside the verified install folder (else `launch-program-refused` 1-4, result 50). It gets `SteamAppId` / `SteamGameId` = the app. The host serves the client's callbacks until the program exits and reports `launch-program-started`, `launch-client-error` 0 (what the app waits for) and `launch-game-ended`. Unset = the normal route, unchanged. Valve's licence and DRM checks are not skipped or replaced; only which of the game's own programs starts is chosen.

App side: `GameFixes.Fix.steamProgram` (Rust: `RustClient.exe`); `SessionController.prepareAndLaunchDock` sets the two variables.
Not verified on a device. Open question: whether the program finds the client hosted inside dockhost.exe the way a game that Valve's client starts does.

**0076 (0.50.127), withdrawn in 0.50.128.** First device run of the 0.50.126 route (swap 4 GB wide): the Steam sign-in worked, the host started `RustClient.exe`, the game reached 99 % loading, then stalled. In the log `steam_api64.dll` asks for `steamclient64.dll` and `load_dll ... steamclient64.dll status=c0000017` (no memory) twice, with `[va-scan] FAILED`: the guest band `0x7000000000..0x73ffff0000` is 99 % occupied (16 365 of 16 384 MB; `[furniture] mapped=16205 MB free=178 MB`; many `[big-reserve]` 512 MB blocks, the emulator's per-thread reservations). The 26 MB library cannot be placed that late, so the game never reaches Steam. 0.50.127 tried to load the client library at the game's start through `AppInit_DLLs` (the host set `LoadAppInit_DLLs` / `AppInit_DLLs` around the run). It did nothing: Wine's `kernelbase!LoadAppInitDlls` is an empty stub (dlls/kernelbase/loader.c), so no AppInit library is ever loaded. Removed again; the host is back to the 0075 behaviour.

**What fixes the address-space shortage (0.50.128).** The engine already has a valve for it: `MADEIRA_CAGE_RELEASE=1` makes `ios_cage_release_on_exhaustion` (virtual_ios.c) hand the unclaimed 8 GB V8-cage holdback (`[cage] holdback reserved 0x7200000000+0x1ffff0000`) to Wine's allocator when the guest band is exhausted. Madeira's own app sets it for every Dock session (ContentView.swift: "A Dock session runs Valve's client headless, with no Chromium, so nothing claims the 8 GB V8 cage holdback"). Porthole's `SessionController` never did, so in every Dock run of this app the holdback sat idle (the Rust logs have the `[cage] holdback reserved` line and never a `[cage] holdback handed` one). Porthole now sets it for a Dock launch and clears it otherwise. This affects every game started through Steam, not only Rust: a game that fills the band gets 8 GB more address space instead of failed loads. Expect `[cage] holdback handed to the allocator` in the log when the band runs out.
