# 0144 DXMT: GPU time per render pass in the in-game profile

`dxmt/src/winemetal/unix/winemetal_unix.c`: `madeira_passprof_start()` / `madeira_passprof_dump(seconds)` (called by the app's SampleProfiler while "Profile where the time goes" runs). While on, each render pass gets a start-of-vertex and an end-of-fragment timestamp in one shared MTLCounterSampleBuffer (stage-boundary sampling, A14+); at command-buffer completion the pair is resolved and summed per kind of pass (size, sample count, colour count/format, load/store actions, depth format). The dump (`[gpu-prof]` lines) lists the 24 costliest kinds: share, ms per second of play, passes per second, ms per pass. The timestamp scale comes from two MTLDevice sampleTimestamps readings 30 s apart.
Reason: The Forest, 2026-10-14: GPU busy 60 % on average and over 80 % in 24 of 59 intervals once the CPU side got faster; 27-28 render passes and 800-1,100 draws per frame at 1280x720 with the lowest settings. Untested on a device.

First log (0.50.343, 2026-10-14 23:19): the pass durations were all ~equal whatever the size (a 160x90 pass as long as a 1280x720 one): start-of-vertex is stamped long before the fragment work of the same pass because Metal overlaps the vertex stages with the fragment stages of earlier passes. 0.50.344: a pass's time is now the gap between its end-of-fragment and the previous pass's in the same command buffer (the first pass: from its own start-of-vertex); the tick scale is calibrated per command buffer (GPUEndTime-GPUStartTime against the timestamps between its first and last pass); the table also estimates the load/store traffic each pass kind asks for (colour and depth bytes x load/store actions) in MB moved per pass and MB/s in total.
Same log: the GPU's busy share alternated between 37 % (13.5 ms/frame) and 88 % (30 ms/frame) at the same 28 fps and ~636 draws: the GPU clock follows the load, so "GPU busy %" does not say the GPU is the limit.
