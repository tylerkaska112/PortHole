# 0146 ntdll: `env.MADEIRA_STEER_PA_FIRST = 1` sends the game's big empty reservations to the free pool range, not the emulator's band

`build/ntdll-unix/virtual_ios.c` (the steer valve in `NtAllocateVirtualMemory`, patch 0077's `steer_pa_first`). It used to be on only in a Dock session (`MADEIRA_CAGE_RELEASE=1`); `MADEIRA_STEER_PA_FIRST=1` now turns it on for any game (a game's own config line `env.MADEIRA_STEER_PA_FIRST = 1`). Off by default; ignored with the 32 GB pool switch (`pa32-soft`), which owns that range. Restart the app between runs when changing it (read once per process). The log shows `[steer] 0077 steered reserves go to [0x7400000000,0x7c00000000) first ... (MADEIRA_STEER_PA_FIRST=1)`.

Reason (Subnautica from the Epic store, 2026-10-15, 0.50.353): the game's main thread made 21 reserve-only 511 MB reservations (10.7 GB, 13 % ever committed), the valve put them in the emulator band 0x7c00000000..0x8000000000 (16 GB, shared with the translator's thread state, call/return stacks and caches), 75 threads in a new thread could not get its 16 MB aligned call/return stack (`[va-scan] FAILED ... STATUS_NO_MEMORY`, `THREADSTATE ALLOC FAILED ... the emulator address band is exhausted`, `arm64ec_thread_init failed c0000017`), and the loading screen froze at 0 fps. The slots 0x7400000000 and 0x7800000000 were both empty. The same message appeared with Rust through Steam on 2026-10-06 (which is why 0077 exists).
How to test: add the line to a game that freezes this way, look for the `[steer]` line, and for `[steer] #N ... above ceiling 0x74...` instead of `0x7c...`; `[slot#1]` should turn from CLEAR to DIRTY and `[slot#3] ... occupied` should drop. Untested on a device.
Library: `gl-lib-0146` (ntdll `virtual` object rebuilt on gl-lib-0144's library).
