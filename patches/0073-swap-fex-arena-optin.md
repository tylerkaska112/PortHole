# 0073 swap tier can back FEX's arena (experiment, off by default)

`virtual_ios.c` (`ios_swap_fex_arena_ok`, `ios_swap_is_fexjit`). Sons of the Forest (2026-10-06, two runs, swap 4096 wide) is ended by iOS at the 6.1 GB footprint limit after 2.5 min (pool 1152 MB) or 4 min (pool 640 MB). At the end `[phys-map]` showed FEX's arena at 1.9-2.3 GB written, many 128 MB blocks 98% dirty and 90% compressed, while the swap tier held only 1.5 GB because `ios_swap_is_fexjit` keeps the whole arena out of it. `MADEIRA_SWAP_FEX=1` (Settings > Engine options > Swap also keeps the emulator's memory, or `env.MADEIRA_SWAP_FEX = 1` on one game's Engine page) skips that exclusion for the arena. Needs `MADEIRA_SWAP_COVERAGE=wide`; broad refuses the band above 0x7c00000000 by its own rule and is unchanged. The JIT pool stays excluded. Logs `[swap] 0073 FEX arena joins the file-backed tier` once. Without the variable the engine behaves exactly as before. What to watch: `[swap] ml1077 stats` (file-backed MB should grow by the arena's cold part; raise swap-mb if `refused` rises), `[footprint]` compressed MB, frame times, and whether the game still runs.

**First device run (0.50.121, Sons of the Forest, swap 4096 wide, pool 640 MB, 2026-10-06).** The switch worked: `fex/jit=0` in the census, FEX's arena was file-backed. While the file had room the footprint stayed low (backed 1411 MB / footprint 923 MB; backed 1637 / 976; backed 4014 / 2420, i.e. 4 GB held in the file for 2.4 GB of footprint), but the 4096 MB offset space was full after about 30 s (`file used 4095 of 4096 MB`, refused 415 -> 5881) while only about 400 MB of real disk was used (`disk 402 MB of 4096 cap`): wide backs each fresh reservation whole, and FEX reserves 128 MB blocks, so the offset space runs out long before the disk does. After that every commit stayed anonymous and the footprint went 2.4 -> 5.4 GB; the game was ended at 6143 MB after 45 s. So: not a failure of the idea, the cap was too small for it. Next test: `swap-mb = 16384` on the game's cfg lines (sparse file, costs disk only for pages the game really writes). If that holds, the proper change is wide's cap counting real disk (as broad does, ml1257) over a large offset space.

**Second device run (0.50.121, swap-mb 16384, SOTF, 2026-10-06, 40 min).** The offset space was no longer the limit (refused 0) and the footprint stayed 1.1 -> 4.9 GB (GPU 3.5 GB of it) while the file held 13.3 GB (7.6 GB of real disk, 8077 hole punches, 3179 backings / 1804 releases in 37 min, i.e. 1-4 operations a second: NOT a high churn rate, so the earlier "frees under the lock make loading slow" guess is not supported). Loading reached about 75 % after ~37 min (the user watched it), CPU mostly 10-30 %: the game's logical memory demand with FEX counted is about 18 GB, far above RAM, so the working set pages between RAM and flash. At 01:45:43 a pseudo-process (tid 0088, a Steam-side DLL image at 0x71fd2fd380, AV write to 0x800010, RDX unreadable) crashed with 0xc0000005 and was torn down; from then every thread waited (`[waiters]` age ~300 s), CPU 8 %, memory flat: the stall is the Steam client dying, whether or not the switch contributed is unknown. Conclusion: the switch does what it was built for (fits the game under the limit) but at 10x or worse load time for this game; no further engine work planned for it. Possible but unmeasured: lower the game's own demand (in-game graphics preset / texture quality).
