# 0030 - Ubisoft Connect's Chromium client: command-line log, and an opt-in single-process gate

**Problem.** `upc.exe` (Ubisoft Connect's client, a CEF/Chromium app) starts `UplayWebCore.exe --type=gpu-process`, renderer, network and crashpad helpers. Each 32-bit process takes one of the few 4 GB guest-window slots (`guest window reserve returned 0xc0000017`, ~8 slots), its own FEX code buffer (the pool tail grew to 512 MB) and image copies; the client window stayed blank white and Far Cry 6 never got its handshake.

**Change.** `build/ntdll-unix/process_ios.c`, next to the existing steamwebhelper gate (task #34): for `...\upc.exe` the command line gets ` --single-process --disable-gpu --disable-gpu-compositing --enable-logging=file`; `...\UplayWebCore.exe` with `--type=` is refused (STATUS_ACCESS_DENIED), so renderer, network and the software-rendered compositor run as threads of the browser process. Log lines `[proc-gate] upc.exe: injected ...` / `REFUSING UplayWebCore --type= child`. On by default (the client cannot run otherwise); `MADEIRA_UPC_SINGLE_PROCESS=0` turns it off.

**Rebuild.** `tools/rebuild_ntdll_object.sh process` (the script knows `process`), copy the library over `vendor/Madeira/app/Madeira/libntdll_unix.a`, restage.

**Unknown.** Whether Ubisoft's own argument parser tolerates the extra switches and whether its CEF build supports `--single-process`. Chromium's debug.log goes to the `cache\http2` user-data dir under `users\mobile\AppData\Local\Ubisoft Game Launcher`.

**0.50.66 result (so the gate is now OFF by default).** With the injection and the refusal on, Ubisoft's CEF kept starting its helpers anyway (it ignores the switches from its own command line: gpu-process x9, renderer x4, NetworkService and StorageService utility x9 each were asked for), and with the graphics helper refused Chromium ended itself: the guest stack at the `int3` decodes to `[...FATAL:gpu_data_manager_impl_private.cc(415)] GPU process isn't usable.`; `UplayCrashReporter.exe` then ran. A full Chromium set is browser + gpu + network + storage + renderer = 5 processes, which fits the ~8 guest-window slots once patch 0031 stops the pool copies.

**Now.** `MADEIRA_UPC_SINGLE_PROCESS=1` switches the injection and the refusal on; by default nothing is changed, and every `upc.exe` / `UplayWebCore.exe` command line is logged in full (`[proc-gate] cmdline(upc|webcore)+N: ...`, 160 characters per line) to see which switches reach the children.

**0.50.68: the white box.** With the helpers allowed, Chromium got gpu, NetworkService and StorageService, then the RENDERER failed to boot: `guest window reserve returned 0xc0000017`. Seven 32-bit processes were alive (launcher stub, upc.exe, 2 x `UplayService.exe`, gpu, network, storage), and there are ~7 usable guest-window slots (0x72, 0x73, 0x75-0x79; 0x74 is lost to the guard of slot 0x73, 0x71 is partly occupied, 0x7a refused by iOS), so the page process never started and the client window stayed blank. No 32-bit process had exited, so nothing was reclaimed. `UplayService.exe -uplayservice_perform_updates` and `-uplayservice_set_app_user_model_id` (an updater and a taskbar-identity helper, both on a pipe back to upc.exe) are now REFUSED (STATUS_ACCESS_DENIED, `[proc-gate] REFUSING UplayService.exe`), freeing two slots; `MADEIRA_UPC_SKIP_SERVICE=0` starts them again.
