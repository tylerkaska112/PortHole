# 0061 - the code around a guest int3 and the guest stack (diagnostic)

0.50.105 log: the game's own unhandled-exception filter is the CRT's `__scrt_unhandled_exception_filter` (it only claims C++ exceptions, 0xe06d7363), so it is NOT what handles Black Ops 3's `int3` on Windows. What the log shows instead: the first `int3` on the main thread (exe+0x...364a0, the same address in the threads it starts) is swallowed by an ntdll-side handler (`RtlUnwindEx ... target=ntdll+...`, no VEH, only GS handlers in the guest chain) and the thread goes on; later `int 0x2d` (bytes `cd 2d`) arrives as an AV at address 0 handled by the protection's VEH; and the last `int3`, in code the protection generates, reaches the process as unhandled. On Windows an unhandled int3 crashes, so either the byte at 0x...364a0 is not an int3 there (padding the flow should never reach, or a byte the protection patches before running it) or a handler exists that we lack. `signal_arm64_ios.c`: first three `[int3-guest]` events also print `[x86_code] int3-code <addr>: <hex>` (0xa0 before, 0x80 after the int3) and 24 qwords of guest stack from RSP. Logging only.

**0.50.106 result and 0062 (0.50.107).** The int3 is in a block of 0xCC padding (0x120+ bytes of `cc`), reached by `call r10` (r10 = the int3's address; rcx = -2 = NtCurrentThread, rdx = 0x11 = ThreadHideFromDebugger: the protection calls a syscall stub it set up), right after its NtUnmapViewOfSection of the clean ntdll copy. Just before: `[alias-own] ml640 #2 0x7050134000+0x4000 prot=rwx OWNED by live anon JIT alias`: the page is memory the game allocated RWX, dual-mapped by the engine. So the stub the game writes there is either not written yet, written through the RW alias while FEX still sees the old bytes (stale translation / detached guest VA, see the ml635/ml640 comments in virtual_ios.c), or lost. 0062: `[int3-guest] alias: page= covered= rw= rx=` and the 48 bytes of the guest VA, the pool RW alias and the pool RX alias at the int3 offset (`alias views ...`); if the RW alias holds code and the guest VA holds `cc`, the guest VA has detached.
