# 0050 - an x64 program that opens a system DLL from System32 gets the x64-compatible build (Black Ops 3)

**Problem.** After 0049 (log of 0.50.88) Black Ops 3's protection opened `C:\windows\system32\gdi32.dll` as a file, created a SEC_IMAGE section, mapped it (0x71f1bf0000, size 0xd0000 - the NATIVE ARM64 build; the EC/x64-compatible gdi32 is 0xf0000) and ran code in it: FEX reported `Invalid instruction in entry block: 71F1C24C92` (the address is the middle of native ARM64 code) and the thread died with c0000005 after ~25 s. The same protection mapped the on-disk ntdll earlier and saw SizeOfImage 0x110000 instead of the loaded 0x130000. Windows for ARM64 gives x64 processes ARM64X/EC files in System32; Wine's System32 here holds the native ARM64 files and the x64-compatible ones live in `sysx64` (the loader's "mixed-arch fallback" already maps LoadLibrary names there).

**Change.** `wine/dlls/ntdll/unix/file.c`, `NtCreateFile` (NtOpenFile calls it): a plain open (FILE_OPEN, no write/delete access, no RootDirectory) of `\??\C:\windows\system32\<name>.dll|.exe|.drv`, directly in System32, by a process whose own image is x64, is first tried as `...\sysx64\<name>`; if that open fails the original open runs. Logs `[sysx64] 0050 <from> -> <to>: <status>` (first 40). `tools/rebuild_ntdll_object.sh` knows `file`.

**Rebuild.** `tools/rebuild_ntdll_object.sh file`, copy the library over `vendor/Madeira/app/Madeira/libntdll_unix.a`, restage.

**Risk.** Every x64 program reading System32 DLLs as files now sees the EC builds (what Windows on ARM shows them). File sizes/versions seen by installers or version checks change accordingly.

**0.50.89 result.** No `[sysx64]` line at all: the redirect never matched (the mapped gdi32 was still the ARM64 build, id c5950f8a..., SizeOfImage 0xd0000 vs the EC build's 0xf0000). 0.50.90 logs every open of a path containing "system3" by an x64 process (`[sysx64] 0050 open <name> access disp root`, first 120) to see the real name or why `ios_x64_process()` is false.

**0.50.90 result and fix (0.50.91).** The log listed the opens (`\??\C:\windows\system32\gdi32.dll`, access 0x80100000, disp 1, root 0) and no redirect: the prefix literal has an upper-case `C` and the compare lower-cased only the name's character, so it never matched. Fixed (both sides lower-cased). The open diagnostic is removed; redirect lines (`[sysx64] 0050 <from> -> <to>: <status>`) are capped at 400.

**0054 (0.50.99), experiment.** With the redirect working (0.50.91+) Black Ops 3 maps the x64-compatible ntdll (1.5 MB) from disk and then spins at 100% CPU for 8+ minutes with identical registers and NO NtUnmapViewOfSection (`[sc] #1/#2` only), while with System32's own (ARM64) ntdll it unmapped after ~13 s and went on. `ios_sysx64_alt_name` now leaves `ntdll.dll` alone (the other DLLs are still redirected) to see whether the protection then reaches the next module with the EC files.

**0063 (0.50.108).** 0.50.107 log: at the int3 all three views of the anon-RWX page (guest VA, pool RW, pool RX) are `cc`: no aliasing bug, the stub was never written. The protection extracts syscall stubs from the clean ntdll it maps as data: with System32's ARM64 ntdll (0054) it finds no `4c 8b d1 b8` stub, builds nothing and calls `cc` padding (int3, `rcx=-2 rdx=0x11` = NtSetInformationThread(HideFromDebugger)); with the x64-compatible ntdll (0.50.91-98) it spun forever. New try: `app/Madeira/arm64ec-windows/ntdll-x64file.dll` = the EC ntdll cut to the end of its last section (0x120000 bytes; the loader's own copy is padded to 0x180000 with zeros), and `ios_sysx64_alt_name` serves `system32\ntdll.dll` as `sysx64\ntdll-x64file.dll` (the farm links every file of arm64ec-windows into sysx64). Other DLLs: as before.
