# 0153 ntdll: BeamNG.drive's Chromium runs --single-process (opt-in with `env.MADEIRA_GLUED_MAIN = 1`)

`build/ntdll-unix/process_ios.c` (`sc_helper_kind`): with `MADEIRA_GLUED_MAIN=1`, `BeamNG.drive.x64.exe` is classed like SocialClubHelper.exe, so the existing Social Club code applies to it: the browser (the game's own program, no `--type=`) gets `--single-process`, BackupRefPtr off, `--js-flags=--jitless` and `--no-proxy-server` on its command line, and a `--type=` child it still starts is refused. The app sets the variable for BeamNG.drive only (`GameFixes`, `gluedPools`).

Reason (BeamNG.drive 0.39.4.0 with CEF 148, 2026-10-16 02:25, build 488): with patches 0151/0152 and `MADEIRA_X64_IMAGE_NOCOPY=1` the game's own process got both PartitionAlloc pools and Oilpan's slot, ran 11 s and drew its window; then it started its GPU, network and storage helpers (`--type=gpu-process`, `--type=utility ...`) and each asked for its own 32 GB PartitionAlloc pool (`[jumbo#6]-#16`, `layout 2: 32 GB at a 32 GB boundary refused`), which the address space cannot give a second time (pseudo-processes share one address space; the map has two such boundaries). Every helper ended with 0x80000003. Madeira's comment at `sc_helper_kind`'s neighbour says the same for Social Club and Steam's web helper: one Chromium process, the rest as threads.
How to test: the log should show `[sc-cef] SocialClubHelper.exe browser: --single-process added; BackupRefPtr off ...` and `cmdline-tail:` with the game's own command line (the text says SocialClubHelper.exe, it is the game), no `--type=gpu-process` spawns and no `abort_process ... 0x80000003`. UNKNOWN: whether BeamNG passes its process command line to CEF unchanged, whether the in-process GPU/renderer work with DXMT, and whether the app's memory (6 GB limit; the 02:25 run was at 6025 MB when the log ends, with five Chromium processes alive) now fits. Untested on a device.
Library: `gl-lib-0153` (ntdll `process` object rebuilt on `gl-lib-0152d`).
